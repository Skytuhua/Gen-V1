# Fixed approved-plan materialization consumer

`WorkPlanClient.materialize(request, context, signal?)` calls only `POST /v1/owner/work-plan/materialize`. It reuses the existing owner loopback HTTP transport, deadline, framing, error/status validation and credential callback. No automatic retry, replacement ID, claim, dispatch or engine action is added.

`request` is the closed issued `{project_id, message_id, plan_ref, work_order_id}` envelope. Retain its stable ID before sending. `context` is independently retained company/project/principal identity plus the complete original proposal request/response and authorization request/response. Both full reviewed records and their original envelopes are cloned before any credential await. Existing work-plan validators verify their signatures, exact request bindings, basis, approval and WorkOrder joins.

The materialization validator checks every task against the retained step in declared order, repository inputs, basis and authorization digests, exact WorkOrder/PlanRef, dependencies, stable task ID, full input digest, approved per-attempt reservation ceiling, task-set digest and signed receipt. It rejects duplicate/foreign/unreviewed records even when their own digests were recomputed. Binding and scheduler-hint digests remain server-owned assertions; they do not prove worker readiness, trusted costs, admission or independent review. All returned steps are ordinary work. A label such as review does not grant review authority.

Whole request/response bounds remain 32768/262144 encoded bytes. The strict legacy work-plan UTF8/JSON/integer codec is reused, not replaced by C01 normalization. After strict parsing, a plain-object clone lets Ajv's `uniqueItems` helper compare multiple task objects without throwing on the parser's null-prototype objects. Duplicate-key, malformed UTF8, non-integer lexical tokens, prototype-key and schema checks remain active. Raw issued schemas/manifests/examples are byte-pinned.

The implementation is trusted-host Node code, not a browser import. The only new runtime JSON asset is `packages/company-contracts/work-order-tasks-candidate.1/tasks.schema.json`; its manifest/examples and the public regression context are not runtime assets. Personal owns exact asset admission. No new Gen route, UI control, startup flag or live service permission is enabled. The current status-only app/service and its credential remain unchanged and cannot call this operation.

An accepted result means TaskSpecs are stored/enqueued, with `task_materialization:true`, `dispatch_authorized:false`, `live_ready:false` and synthetic-only evidence. Earlier authorization/read receipts retain their original `task_materialization:false` fields. An exact replay is historical acceptance, not renewed approval or an instruction to run. Explicit same-ID replay is available after a lost outcome; the caller must not silently rebase, renew expiry or invent another ID.
