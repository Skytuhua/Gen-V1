## OBJECTIVE

A rough idea often omits the desired outcome, useful constraints, or a way to know the work is done. Add one explicit **Enhance prompt** click that rewrites the current draft in place into an editable, clearer user request, grounded in the owning project's approved context where available. Keep the user in control: one click makes one rewrite request, creates zero threads or messages, and never sends to the agent. Only a later explicit normal Send submits the text the user actually sees and edits.

## REQUIREMENTS

| ID | Requirement or scope decision |
| --- | --- |
| R1 | One click on a nonblank eligible draft in an idle primary conversation composer, including a new conversation before its first send. Use project context only when its approved owner can be established. Without admitted context, rewrite the draft alone. Do not add the action to Side Chat, delegate/inventory input, or other generic forms. |
| R2 | Replace only the draft text on a current success; preserve the user's language, intent, concrete names and explicit constraints. Organize into a desired outcome, constraints and checks where useful, without inventing requirements, permissions, paths, or facts. No commentary, auto-send, new thread, changed model selection, attachments, excerpts, skills, source bindings, or send-mode mutations. |
| R3 | Use an eligible already-configured text model and account; never silently swap to a different provider/account. No new settings UI, provider credential workflow, project indexing, chat history ingestion, workspace search, fallback agent run, or feature-flag milestone activation. |
| R4 | Protect unsent text. Leave the input editable and Send usable subject to existing rules while enhancing. Editing, moving scope, starting Send, or cancelling invalidates pending results; stale and failed results leave the draft untouched. Offer one local Undo after success, valid only for the unchanged enhanced draft in the same scope; a fresh click after failure retries the current draft. |
| R5 | Require authenticated local API + CSRF and an isolated, bounded, tool-free text request. Only the requested draft and approved project text may go to the configured model; no transcripts, code tree, attachments, terminal output, memory, raw paths, credentials, or unreviewed plug-in/project data. No prompt/result logging or durable auxiliary conversation. |
| R6 | Adopt the visual, accessibility, responsive layout and motion spec below. A keyboard or screen-reader user must be able to request, cancel, revise, undo and Send without a focus trap. |
| R7 | Demonstrate repeatability with deterministic tests, and verify a real eligible provider in an authenticated local installation using synthetic content before calling the feature ready. After verification the implementing agent sends finished work to the front end team **for review**, not for design. |

## DESIGN

### Request and model admission

- Proposed route: `POST /api/composer-enhance`, strict JSON `{draft: string, target: {kind: "thread", threadId: string, modelId?: string} | {kind: "new", modelId: string}}`, response `{draft: string, usedProjectContext: boolean}`. The optional model ID conveys the visible composer choice only for an unbound thread. No account, resource/grant, project root, scope digest, source content, or filesystem path in the request. Use the authenticated client helper, host's origin/session/CSRF checks, request body cap of 64 KiB (including JSON encoding), and `Cache-Control: no-store`. Validate draft nonblank and at most 8 KiB UTF-8; don't silently clip it. Parse the success response strictly and validate nonempty, bounded output on host and client.
- Resolve an existing primary thread, status, project/workspace identity and credential binding server-side. Only idle ready/completed main threads without archived, side/delegate, retry, active lease/run, pending input or blocking operations qualify. For a model-unbound eligible thread validate the submitted composer model using the same host-resolved account binding and model admission as initial Send; if absent or invalid, return unavailable rather than guessing. A bound thread uses its established binding, not a client override. For new drafts validate the supplied composer model against the current host/account binding, without doing a thread-creation command, and use draft-only context. Resolve the existing functional Text generation model preference first **if** T01 finds and verifies it; otherwise use the bound conversation model or selected new-draft model with existing account checks. Never unbind a conversation or use an unapproved account even if a preference requests it.
- Start with the verified-in-code Pi in-memory pattern; no official/CLI adapter is eligible until the implementing worker can demonstrate equivalent in-memory, tool-free behavior. Use a separate rewrite purpose, strict per-purpose input and output limits, a synthetic auxiliary run identity and null session path, no resources (including no original task directory access), no history/follow-up/compact, no skills, and a tool-denying host callback. Use the configured provider's managed credentials; don't serialize those credentials into the prompt. An unsupported model, offline host or missing account must not start an agent or switch accounts. Route errors use the existing safe envelope: validation (400/413), not found or unavailable owner (404), stale/busy (409), unsupported/unavailable (503), provider failure/invalid output (502), timeout (504). Client substitutes fixed local messages, never raw provider diagnostics.
- One active rewrite per host, no queue or auto-retry; return busy if the slot is occupied. Give foreground work precedence using the host's cancellation/credential/update lifecycle: cancel a rewrite before the normal work consumes the same capacity or binds altered credentials. Abort unfinished HTTP responses; attach a 15s worker deadline across capture, inference and settlement, cancel/dispose the isolated adapter on all exits, and retain its slot until cleanup completes. Ignore later events and reject mismatched run identity. Do not instantiate an adapter until initial admission succeeds.

### Approved context and rewrite

- Capture only explicitly approved `AGENTS.md`, `CLAUDE.md` or `GEMINI.md` inputs admitted through the existing path checks, physical file guards, restricted names and grant limits. Factor shared guarded read logic as needed in `approved-project-context.ts`; preserve its current run binding, precedence, output and tests. For the separate idle mode, take current grants from the host store for the exact authorized thread/project/workspace, confirm the host-trusted working copy association, and recheck archive/status/epoch, workspace binding, grants digest, model/account and abort before reading, just before model dispatch, and again before returning. Do not dispatch from a stale closure. On grant/owner revocation after dispatch, cancel if still pending and discard output; data already sent to the configured provider cannot be recalled. New drafts have no approved thread grants; a selected project name is not authority. Missing eligible files or absent context produce draft-only results; an ownership or custody failure must not substitute a broader source or send questionable bytes.
- Retain at most 8 KiB UTF-8 of bounded project snippets in existing precedence order; use code-point-safe clipping and keep only admitted text plus safe filename labels, never absolute paths, resource IDs or manifest headers. Build a bounded JSON frame of `draft` and `projectNotes` as quoted data; the system instruction tells the model to rewrite, not execute, to ignore directions embedded in notes or requests to reveal hidden/system material, and not to echo project instructions wholesale. It should preserve meaning and language, use short headings/bullets when helpful, and state unknowns as questions rather than fill them with guesses. Keep the entire framed input below 40 KiB UTF-8; if serialization exceeds that bound, remove project lines/notes before considering request failure. Verify account/model consent and isolation before sharing any approved context; this is a user-triggered provider call, not a background read or silent transmission.
- Ask for only JSON `{"draft":"..."}` with one key and no fences/preamble. Accept up to 8 KiB UTF-8 decoded draft and cap raw result bytes at 24 KiB and provider output at 3,072 tokens; reject blank, malformed, over-limit, or control characters other than line breaks/tabs. A response indistinguishable from the input after outer-whitespace trim is a no-change outcome, not an Undo entry. Treat every result as plain textarea text, never execute/interpolate it into HTML or commands. Do not publish generation content into conversation events, logs, persisted auxiliary sessions, host journal, or analytics; only a successful draft edit is persisted through normal client draft recovery. No migrations or new dependencies; reverting feature wiring must leave ordinary saved drafts and sends readable.
- Synthetic example: draft “fix overflowing toolbar when narrow”; an approved note says “The toolbar is in ComposerToolbar.tsx; preserve the existing keyboard order.” An acceptable result is “Fix the composer toolbar so controls remain reachable in narrow panes. Preserve keyboard order. Verify the toolbar does not overflow in a narrow pane.” With no note, it must not invent a filename or breakpoint.

### Composer state and visual specification

1. Render a native `type="button"` after Voice and before Send, inside the existing model/voice control group; widen its accessible group label to include draft tools. Idle: a 16px outlined sparkle plus “Enhance” in an existing 29px-high `composer-tool`, 7px radius, muted foreground, themed hover/focus treatment. Accessible name “Enhance prompt”; title “Rewrite this draft before sending”. At container widths ≤610px use icon-only within a stable 32px slot and preserve the accessible name; at ≤355px allow only the runtime control row to wrap if needed rather than clipping Send, context, voice or model picker. No portal, overlay, new palette, or width change between idle and pending.
2. Disabled when empty/over limit, not ready, busy/working/retrying, inactive/held/covered, or the host/model is known unsupported; put the relevant short reason in the composer status region when the user has entered text and the control is otherwise available. Disable while an IME composition is active; do not change Enter/Tab behavior. If the reason is unavailable model, text is “Enhance is unavailable for this model. You can still send your draft.” In the allowed state, if requested, record owner (thread/draft key, project/workspace, model), draft generation and exact text, request token and abort controller. Dismiss any ghost prediction and suppress it while pending; no interaction with its cancellation endpoint.
3. Pending: use the same focusable button as “Cancel enhancement”, swapping its glyph to a small stop square and its wide text to “Cancel”; retain the previous width. Put “Enhancing draft…” in a polite status region above the footer; a 12px inline ring next to that text rotates linearly every 900ms. Honor reduced motion with a static ring and no transitions or transformations on the new control. Keep Send, typing and voice behavior unchanged; edits from any of them revoke the request. Explicit Cancel aborts and restores idle with “Enhancement cancelled. Draft kept.” No Escape shortcut that could conflict with command suggestions.
4. Before applying, recheck the token, current scope and eligibility, text and generation; use the existing journal conditional-write path against the captured generation (for shared drafts, add the equivalent conditional edit through the shared owner). A new generation invalidates even an edit-and-revert to identical text. Do not preview speculative text before the conditional edit succeeds. Invalidate immediately on typing/paste/dictation/command edits, draft owner or current binding changes, Send initiation, loss of active surface, IME start, or unmount. Late resolution after abort must be inert, including stale error and focus updates. Do not steer focus from an unrelated control; if the request button still owns focus at a valid success, focus the textarea and place its caret at the end. If the textarea already has focus and hasn't changed, preserve focus and place the caret at the end.
5. Success: render “Draft enhanced. Review or edit before sending.” with a text **Undo** control next to the message in the same status row; preserve the exact original whitespace. Use a one-shot 160ms fade-in for status, not the textarea and not a typewriter animation; make it instant under reduced motion. Undo conditionally restores the prior text only if the owner, replacement text and resulting draft generation still match. Clear Undo on another edit, rewrite, send, owner change or unmount; when the focused Undo disappears on use, return focus to the textarea. For no change, show “No changes suggested. Draft kept.” No success state disables Send.
6. Current failure: show inline “Couldn’t enhance this draft. Try again.” for provider/invalid response; “Enhancement timed out. Try again.” for deadline; “Enhance is busy. Try again.” for busy; use the unavailable copy above for unsupported models. Keep the source text and normal edit/Send eligibility; no toast disappears on a timer. Use a single polite, atomic live region for status text, native focus-visible styling and existing light/dark contrast tokens. Test that pointer interactions do not submit or cause scroll/focus jumps, and that the controls remain operable by keyboard at narrow widths and zoom.
