# Fix plan (rev 1) — Typed error taxonomy for the server API

## META
- Feature: one typed error model shared via `packages/contracts`, applied to `apps/server` routes, with per-code UI recovery messages
- Repo: github.com/skytuhua-org/Gen-V1
- Plan revision: 1 — 2026-11-20
- Baseline: `main` @ `7ef0710c90a479233f8dd9fe484a296f8c3c86d3` (verified)
- Issue: https://github.com/skytuhua-org/Gen-V1/issues/1063
- Status: reviewed; route/error census below executed on baseline
- Provenance: devin-a-cloud-b7d3e9 (review/planning)

## OBJECTIVE
Today server errors reach the UI in three shapes: `{error:{code,message,details?}}` (the dominant shape, produced by `HarnessError` through `app.setErrorHandler` in `apps/server/server.ts:71` and `apps/server/device-pairing.ts:345`), the bare `{error:'string'}` sends in `apps/server/host.ts:108-109`, and route-local ad-hoc throws. Codes are untyped free strings — ~200 distinct `new HarnessError('<CODE>')` sites across `apps/` and `packages/` — so the UI cannot exhaustively map them to recovery copy. Goal: a single `ApiError`/`ErrorBody` contract type, a canonical `ApiErrorCode` union, every server route emitting the shared shape, a contract test enforcing it, and a `recoveryMessage(code)` map in the web app so each error code renders a consistent recovery action.

## REQUIREMENTS
- In scope: `packages/contracts` (new error module), `apps/server/*.ts` (all `code(N).send({error…})` sites + the two `setErrorHandler`s + `host.ts` raw-string sends), `apps/web/src/api.ts` + a new recovery-message map, `tests/` contract test.
- Out of scope: changing thrown codes inside `packages/core`, `packages/runtime*`, `packages/workspace` (they already throw `HarnessError` and continue to); files touched by open PRs — notably `apps/server` changes in #1071/#1072/#1078/#1082/#1086/#1087/#1094 and UI files in #1101/#1109/#1113/#1142/#1143 (re-run `gh pr list` before each PR in the series); no behavior change to success paths.
- Design decision (chosen): extend the existing `HarnessError`/wire shape rather than invent a second taxonomy — it is already the wire format on most routes and the UI's `ApiError` already reads it.
- Compatibility: the wire body stays `{error:{code,message,details?}}`; only type-narrowing, never shape change. Rollback = revert the series; no data migration.
- Security: no secret values in `details`; `INTERNAL/HOST_ERROR` keeps the generic message (no stack paths) — current handler behavior preserved.
- Accessibility/UX: recovery copy is sentence-case, states the action the user can take (retry, reconnect, refresh, re-authenticate), never exposes stack text.

## DESIGN
1. `packages/contracts/errors.ts` (new file, re-exported from `packages/contracts/index.ts`):
   ```ts
   export const API_ERROR_CODES = [ /* union literal list from T02 census, sorted */ ] as const;
   export type ApiErrorCode = typeof API_ERROR_CODES[number];
   export interface ErrorBody { error: { code: ApiErrorCode; message: string; details?: unknown } }
   export const errorBodySchema = z.object({ error: z.object({ code: z.enum(API_ERROR_CODES), message: z.string(), details: z.unknown().optional() }) });
   // HarnessError.code narrows from string → ApiErrorCode (constructor arg type changes; all existing throws compile unchanged because their literals are in the union).
   ```
2. Server: keep `app.setErrorHandler` logic but type `code` as `ApiErrorCode`; add a tiny helper `sendError(reply, status, code, message, details?)` in `apps/server/errors.ts` and convert every inline `reply.code(N).send({error:{…}})` to it; convert `host.ts:108-109` to `sendError(reply,503,'HOST_STARTING','The local harness is starting. Try again shortly.')`; convert `conversation-read-routes.ts:19` and `tool-effect-read-routes.ts:22` raw `Error` throws to `throw new HarnessError('CAPABILITY_DENIED', …)`; unify `device-pairing.ts` handler to the same helper (keep its `known||malformed` message rule).
3. Status mapping becomes explicit and exported for the contract test: `API_ERROR_STATUS: Partial<Record<ApiErrorCode, number>>` — `NOT_FOUND`→404; `AUTH_REQUIRED`,`CSRF_REQUIRED`,`LAUNCH_TOKEN_REQUIRED`→401 (fix: today `AUTH_REQUIRED` maps 403 inside setErrorHandler but 401 at the route hook — unify on **401** and note the change in the PR body); `CAPABILITY_DENIED`,`INVALID_HOST`,`INVALID_ORIGIN`,`PERMISSION_REVOKED`,`DEVICE_GRANT_REVOKED`→403; `RATE_LIMITED`,`STREAM_LIMIT`→429; `RESOURCE_LIMIT`→413; `UNAVAILABLE`,`HOST_STARTING`,`HOST_CLOSING`,`PLUGIN_UNAVAILABLE`,`INTEGRATION_UNAVAILABLE`,`*_UNAVAILABLE`→503; everything else known→400; `HOST_ERROR`/unknown→500.
4. UI `apps/web/src/error-recovery.ts` (new): `export function recoveryMessage(code: ApiErrorCode): string` — exhaustive switch over families with concrete copy, e.g. `AUTH_REQUIRED/AI_AUTH_REQUIRED` → "Reconnect to the local host and try again.", `CSRF_REQUIRED` → "Refresh the app, then retry the action.", `NOT_FOUND` → "This item no longer exists. Refresh the view.", `REVISION_CHANGED/WORKSPACE_CHANGED/SOURCE_CHANGED` → "This changed since you opened it — refresh and retry.", `RATE_LIMITED` → "Too many attempts. Wait a minute and try again.", `RESOURCE_LIMIT` → "This request is too large. Reduce its size and retry.", `*_UNAVAILABLE` family → "This capability is temporarily unavailable. Try again shortly.", `APPROVAL_REQUIRED` → "Approve the pending request, then retry.", `CANCELLED*` → "The operation was cancelled.", `TERMINAL_ENDED` → "This terminal has exited.", `GITHUB_AUTH_*` → "Reconnect your GitHub account, then retry.", `PI_CREDENTIAL_LEASE_*` → "Sign in to the provider again to renew the credential.", `PRECONDITION_FAILED` → "A precondition failed. Refresh and check the prerequisites.", `ACTION_UNCERTAIN` → "The action may already have run — refresh status before retrying.", default → "Something went wrong on the local host. Try again." `api.ts` `ApiError` gains `get recovery(): string` (or callers call `recoveryMessage(error.code)`); each error-surface call site (WorkspaceSurfaceBody setError, TerminalBody, files read, SkillLibrary detail errors) renders `recoveryMessage(code)` beside the raw message.
5. Contract test `tests/api-error-contract.test.ts`: (a) statically asserts every `new HarnessError('X')` literal in `apps/server`, `apps/web` and route-adjacent packages resolves to a union member — enforced automatically by narrowing `HarnessError.code` to `ApiErrorCode` (typecheck IS the test); (b) runtime test: build a Fastify instance via `buildServer` test seam or a minimal handler exercising `sendError` + `setErrorHandler`, assert every thrown `HarnessError` yields `errorBodySchema`-valid JSON with the mapped status; (c) assert `recoveryMessage` returns non-empty for every `API_ERROR_CODES` member (exhaustiveness test via a `satisfies` record).
