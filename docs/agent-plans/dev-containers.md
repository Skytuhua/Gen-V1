## OBJECTIVE

Today a project's interactive terminal and saved scripts run with host tools, and the agent's approved repository test executes the host Node binary. A local main thread should be able to use the tooling declared by its project's dev container instead, without sending those commands to the host or confusing the working copy with the original checkout. Docker supplies a workload boundary, not a guarantee against hostile images or a substitute for host tool authority.

Success means that, on the installed Windows app with a local Docker Desktop Linux engine, the agent's approved test, the thread's terminal and its saved script all observe the expected container cwd and container-only tooling. A write in the container appears in the selected working copy and its Gen diff, not the original checkout when using a managed worktree. If the container cannot run, no equivalent host command starts; the UI shows why and how to recover.

## DESIGN

### Host control plane and containment

1. **Discover and review.** Resolve owner from the host's admitted thread/project binding, never a renderer/model path. Read bounded regular config/build inputs from that checkout; reject traversal, reparse-point/symlink escape, or the private Git family as a build/mount source. Canonical effective inputs include the source path/identity, config bytes, Dockerfile/context identity and content, immutable image identity, exact lifecycle invocation and selected environment variable names. Review an image reference or build definition first; if resolving/building it reveals a different effective policy or additional behavior, halt before create/exec and require a new review after validation. Pin the resolved image for create/reuse. Exclude host app data, user profile, credentials and Git admin metadata from each build context, even if checkout layout or a Dockerfile requests them. Label external pulls/build network as such; don't claim an air gap.
2. **Provision and execute.** Proposed new host service `packages/workspace/dev-containers.ts` owns lifecycle; isolate tool invocation in a sibling adapter. Adopt a pinned `@devcontainers/cli` behind the adapter, using `up`/equivalent provision and `exec`/equivalent admission after validation; invoke a verified binary with an argv array, minimal env and no host shell. Verify the engine is local, running Linux containers, and that actual image/container user, labels or equivalent ownership identity, mounts and policy match before any workload runs. Use `/workspaces/project` by default; accept a safe absolute POSIX workspace folder inside an exactly approved workspace mount sourced from the bound checkout, with the default writable project bind. Reject extra `mounts`, substitutions that reach host env, and implicit execution from merged image metadata unless explicitly supported, validated and reviewed. For `postCreateCommand`, run once inside the newly created owner container and only after effective policy validation; keep lifecycle disabled during unchecked provisioning. If the CLI cannot separate inspect/creation/hooks enough to enforce these rules, block implementation at T01. The alternative is a raw Docker adapter for a narrower explicitly implemented subset (not a fallback at runtime); revise and reapprove the plan before proceeding.
3. **Keep Git and execution authority distinct.** Bind only the attested working files; leave host `.git` pointers untouched, and never grant container-side resolution to the private family. Verify a container write is observed by host `ProjectTools.gitStatus`; document that Git admin operations belong to Gen's host controls. Tool authority, receipt preparation and grant verification stay on the host. For an agent test bind approval to the declared relative test file, container executable/argv, logical cwd, ready generation and effective config digest; use container Node and revalidate before dispatch. Terminal uses a host PTY around the verified container exec adapter with an interactive POSIX shell, not a host shell; a saved script uses that same channel. Disable or separately prove any provider/integration path that could run a thread workload on the host.
4. **Contracts and state.** Proposed strict Zod contracts in `packages/contracts/dev-containers.ts` and owner-checked routes in `apps/server/dev-container-routes.ts` registered by the existing Fastify host: read status/config preview, update project opt-in, set thread target, request review/approve, cancel, stop, and inspect/retry. Carry no client-supplied mount path, executable, engine endpoint, lifecycle command or container ID. Persist project opt-in and thread selection separately from lifecycle receipts; key the binding by project/thread/workspace identity and generation. Receipts/status carry revision, state, safe reason/details, reviewed config digest, and action availability; send neither secrets nor raw Docker arguments to the renderer. Use bounded diagnostic redaction and the existing local origin/session/CSRF protections. Do not expose state in remote/read-sync payloads in v1.
5. **Lifecycle.** Host is the default selection, not a fallback. For a selected container, states are `unavailable | review-required | starting | ready | stopping | stopped | failed | recovery-required`. Approve enters starting; start reaches ready only after engine, ownership and effective policy checks and confirmed hook completion. A failure with known result enters failed; uncertain effect enters recovery-required and blocks commands. `Stop`/successful cancel reaches stopped only after confirmed teardown of workload processes; don't kill another thread's processes or remove worktree files. Cancel in flight may show stopping; if teardown cannot be confirmed, enter recovery-required. Review expiration/config change blocks new launch and invalidates Ready; stop existing workload before admitting the replacement. On restart inspect only known owned resources against receipts; recover a proved ready generation without replaying a hook, otherwise require an explicit recovery action. Explicit retry from a known failed/stopped state revalidates approval; changed inputs return to review. Reuse neither terminal IDs nor container generations after they end. Switching to Host requires a separate explicit user action after command/terminal shutdown and no unresolved effect. Serialize state changes per owner and return typed conflicts for stale revisions.
6. **Rollout/rollback.** Ship default off. When the host gate is turned off or a project disables opt-in, stop or fence the app-owned workload, disable new container launches, and preserve the Container selection as blocked until the user deliberately switches. Persisted receipts are inert, and checkout/worktree files remain intact. Do not silently delete user data or arbitrary Docker resources. No schema backfill for Host threads.

**Effective configuration exceptions.** An image pull or build can reveal metadata unavailable during the initial review. Unsupported effective metadata is blocked, never stripped and then silently trusted. If supported metadata changes what the user would approve, return to **Review required**, display “The resolved image changed this configuration. Review it again before starting.” and repopulate the same review modal with the resolved image and effective values. Discovery and provisioning must turn off CLI defaults that make the Git root a broader mount or probe an interactive user environment before approval.

### Visual design and motion

**Settings.** In **Settings → Projects & Working Copies**, add a supported searchable row titled **Dev containers**, after the connected project control (or first item in that section if there is none). Search terms: `docker devcontainer container isolated terminal workspace worktree`. Use the existing settings row grid and shared `Select` for local project selection (do not auto-select when ambiguous), then a labeled switch **Allow dev containers for this project**, off by default. Helper: “Lets you select a dev container in this project’s threads. Commands stay on the host until you select one.” With no project, replace the switch with “Connect a local project to use dev containers.” If host capability is off show “Dev containers are not enabled on this host.” While saving keep the prior value visible, disable the switch and show “Saving…”; on failure retain the last saved value and show “Couldn’t save the setting. Try again.” When disabling an active project, show the shared confirmation modal: **Disable dev containers?** / “Container commands will stop or be blocked. Threads won’t switch to the host automatically.” / **Keep enabled**, **Disable**. Settings results focus the row, not an implicit toggle.

**Thread and terminal.** In the main conversation `App.tsx` composer, put an execution target button at the leading edge of the secondary action area of `ComposerToolbar`, adjacent to the project control and before Changes/Create PR. Hide for ineligible threads or unused projects when the gate is off; preserve a blocked control for an existing Container selection. The button opens shared `Popover` content with target/actions and a one-line reason. Make selected target explicit (text, not a tooltip), use Lucide 16px icons with `aria-hidden`, then label, then a decorative `ChevronDown`. Use `--ui-space-2` (8px) gap and `--ui-row-compact` (32px) minimum height on wide layouts; at a composer width below 480px, wrap the control onto its own full-width first row of the secondary action area, use `--ui-row-touch` (44px), allow labels and messages to wrap, and keep composer/Send visible without horizontal scrolling. Align the shared popover to start, with its built-in viewport collision bound. In `TerminalBody.tsx`, place a non-interactive **Host** / **Dev container** badge with matching icon at the leading edge of the terminal toolbar, before terminal actions. An already-open terminal never changes badges on selection alone. A blocked opening shows the same reason instead of connecting to a host PTY.

**Review.** Shared `Modal`: title **Review dev container**; opening text “Gen will use this configuration to run this thread’s commands. The container can change files in the selected working copy.” Vertical definition list in this order: **Project and working copy** (project label and checkout kind/branch if available), **Configuration** (checkout-relative path), **Image or build** (reference/digest when known, or relative Dockerfile/context), **Workspace access** (selected copy → container folder; “Read and write”), **User** (requested user or “Image default”), **Environment** (names only or “None”), **Setup command** (reviewed command as selectable text, or “None”). Show a non-dismissible warning, “Only continue if you trust this configuration. Build and setup code can run in Docker; no host secrets are shared automatically.” Blocked configuration adds safe field and reason and hides the approval button. Footer: **Cancel** (initial focus) and **Trust and start**; approval closes the modal and returns focus to the stable thread control. Use `--ui-dialog-inset` (24px), `--ui-space-3` (12px) between rows, and wrap values/buttons at narrow widths; shared modal body scrolls vertically with footer remaining reachable by tabbing. Never truncate a reviewed command without a way to read it.

**Interaction.** Use shared focus ring and theme semantic text/surface tokens, with success only supplemental and errors readable in both themes. Shared Modal traps focus and supports Escape; dismissal never approves. Popover supports Escape/keyboard navigation and returns focus to its trigger. On thread navigation park focus using existing focus-retention behavior if the trigger unmounts, and ignore stale status from the prior owner. Terminal label and button expose the target to screen readers. One polite atomic live region announces meaningful state transitions once, not poll ticks, logs or animation; show failure detail as persistent text and do not steal focus on asynchronous updates.

**Motion.** Use the shared Popover and Modal, with their popup timing and easing: `--ui-motion-popup-enter` (180 ms) with `--ui-ease-enter` and `--ui-motion-popup-exit` (140 ms) with `--ui-ease-move`. For these feature instances use an opacity-only enter/exit, opting the Modal out of its default scale and the Popover out of translation without changing other instances. Full motion: fade the changed status in over `--ui-motion-status` (160 ms) with `--ui-ease-move` in a stable layout; animate the loading glyph only while starting/stopping (one neutral linear rotation per second). No scale, bouncing, auto-scroll, or success pulse. Reduced motion: no rotation or positional movement; status changes immediately and overlays use only an 80 ms fade (`--ui-motion-press`), honoring OS preference and app policy. Off: all changes instant, no transition or animation. State text and interactive availability update immediately regardless of animation.
