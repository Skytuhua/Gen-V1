## Deletion storage and restore guarantee

The authoritative fence is a sibling of the canonical profile directory, named `.gen-memory-deletions-<sha256(canonical-profile-path)>.jsonl`; the path key is case-normalized on Windows. A local `project-memory-deletions.jsonl` mirror remains inside the profile. [Storage protection](../../../packages/core/security.ts) denies access to either ledger through direct or ancestor resource grants, reserves peer-profile fence names, and rejects ordinary-name hardlink aliases. The ledger is an ordinary private file, not a symlink or multiply linked file.

Enrollment stores the authoritative fence's path, device and inode in `projectMemoryLedger`. Accepted recall and admitted memory operations fail closed if the enrolled fence disappears, changes identity or cannot be read safely. Forget writes the authoritative fence before its local mirror and SQLite mutation. The durable exclusion therefore precedes any acknowledgement of the reviewed change. Existing local deletion records are carried into the authoritative fence during enrollment.

The protected sibling survives SQLite-only restore and an in-place restore of all profile contents when the parent fence and physical profile enrollment survive. Startup reconciles the fence before serving memory, recomputes collateral source dependencies against restored projections, and durably extends affected artifact IDs before invalidating replayed indexes. A failed enrollment commit is retried before opt-in can succeed. Restored item revisions, excluded source snapshots or affected derived artifacts make purge pending again. These behaviors are covered by the [forget tests](../../../tests/memory-forget-v3.test.ts) and [storage-boundary tests](../../../tests/memory-storage-boundary-v3.test.ts).

This is an application storage boundary. A rollback of the whole parent directory or whole system can roll back the authoritative fence too and is outside the guarantee. An unsandboxed process running as the same operating-system user can bypass application file-grant checks and is also outside the guarantee. No external monotonic anchor, operating-system sandbox or protection against arbitrary same-user code is claimed. Copying/recreating a profile or replacing an enrolled project directory does not automatically authorize adoption of the old physical identity's memory.

Forget's source exclusion is digest-based. If another claim uses the same source bytes, it also becomes unavailable for recall, and its referenced derived indexes are named and invalidated by the deletion preview. This conservative collateral exclusion prevents a renamed source ID or older summary from restoring the same forgotten evidence. Source lookup also checks current selected-thread authorization and, for file snapshots, the original resource-grant identity.

Physical purge removes only permitted local memory items, immutable revision copies, conflict/use projections, excluded source snapshots and affected derived indexes. It preserves tombstones, both deletion ledgers, configuration and original conversation/file history. Maintenance considers a bounded item batch and removes at most 256 entity rows per call using scoped indexes; the host timer retries every minute. Completion requires no remaining retained memory copies and a successful WAL checkpoint. A reader holding old WAL pages keeps purge pending. This is bounded deletion work, not a benchmarked wall-clock latency promise.

## Migration and rollback

1. **Additive installation.** M05 adds separate entity kinds and scoped SQLite indexes through `CREATE INDEX IF NOT EXISTS` when the memory host is initialized. It does not rewrite task-note records, Hermes skill files, native sessions, existing grants or strict UI preferences. No dependency or lockfile migration is introduced. Existing source history is not imported automatically.
2. **Explicit enrollment.** A newly enabled project requires host activation, an authenticated user action and an explicit source-thread set. The authoritative deletion file is enrolled before accepted recall can operate. Forget of retained records also ensures enrollment. Both ledgers and the SQLite enrollment record are part of the retained deletion state; enrollment only completes after its metadata transaction commits; legacy local records are copied forward rather than discarded.
3. **Operational rollback.** Keep `memory.projectV1` and `memory.externalRecallExperimentV1` false and disable opted-in project scopes. Injection/extraction are already absent in this bundle. Authenticated review and permitted edits of retained records remain available, subject to source authorization and revision checks. Disabling does not require an obsolete source thread to become eligible again. Tombstones and purge maintenance remain active, including while the host activation flag is off.
4. **Retain deletion state.** Preserve the M05 entities, authoritative sibling, local mirror and storage protection while disabling the feature. Existing task notes remain the fallback without copying M05 claims into them or into Hermes skills. Removing the deletion files, restoring the complete parent storage tree, or reverting to code that does not enforce the fence is not the validated rollback procedure. No automatic migration between physical profile/project identities is provided.
