# M04, M05, and M06 original-requirement audit

## Decision

**This audit does not provide full release signoff.** It repairs reproduced correctness and user-interface defects, verifies specific core and browser paths, and records required implementation and validation work that remains. The complete test snapshot was not green. Later focused fixes have their own evidence; they do not turn an earlier broad run into a final combined green run.

M04 has a production request compiler and actual compaction plumbing, but several required helpers lack production composition and semantic compaction claims exceed the evidence. M05 has substantial production opt-in, extraction, recall, review, exclusion, and Forget integration. Its actual-host browser test uses the App, authenticated HTTP, Service, and SQLite with explicitly scripted runtimes. M06 now rejects several reproduced false-green conditions and presents exact check details, but production execution, approval, browser, QA, and repair composition remains incomplete.

The [requirement matrix](m04-m06-review-20261117/requirements.md) separates missing implementation, implemented paths awaiting evidence, and optional experiments. The [evidence ledger](m04-m06-review-20261117/evidence.md) identifies exact source trees, the 24 focused code/test PRs, result scopes, and the observed CI state.

## What the review established

### M04: production context work is partly connected

`RequestContextCustody.finalize` calls the compiler. The custody object owns a reusable compiler, but draft preparation advances its generation; `host-context-projection` creates a fresh compiler. The native history API supplies whole history rather than a sequence delta. These facts do not demonstrate the intended append reuse or provider cache benefit. Instruction discovery/conflict presentation, repository-map composition, next-budget application, and relevance observers also need to be distinguished from existing pure helpers. See [request custody][request-custody], [compiler][compiler], [host projection][projection], and [Service][service].

Progressive tool exposure, discovery/describe, per-request frozen schemas, and native dispatch denial are production-wired. Owned result retrieval is also wired, with a private vault and owner/run/epoch/account/workspace/model/invocation checks. General additional-tool and domain results still return directly; extending spilling requires resource-grant lineage. M15 source chips and capture controls are existing production paths. See [progressive tools][progressive-tools], [result custody][result-custody], and [source workbench][workbench].

The repaired compaction path owns its maintenance epoch and enforces checkpoint, compare-and-swap, native callback, and queued-send ordering. Its current production semantic projection still contains empty or unknown unresolved-reference, tool-pair, source-interval, retained-tail, summary, reduction, and cost fields. Native archival exists upstream. This review neither certifies semantic zero loss nor claims that active-history replacement destroys that archive. See [compaction][compaction], [Service][service], and [PR #526][pr526].

The optional precompute helper remains off and lacks a native API to apply a prepared summary. Its lifecycle repair counts settled failed or discarded helper work, but injected `costBytes` is not live provider billing. It is not a demonstrated production latency improvement. See [PR #527][pr527].

### M05: the main host lifecycle is connected

Production extraction admission and a model-only extraction runtime are wired in [hermes-service][hermes-service] through the [memory host][memory-host]. Native checkpoint callbacks are also wired. These are implemented paths whose live or installed evidence is incomplete, not merely uncalled interfaces.

[PR #532][pr532] exercises the actual App, cookie and CSRF checks, HTTP routes, Service, and SQLite Store. Starting with empty memory, the user enables memory for an opted-in source thread, obtains a proposal from settled scripted output, views its pinned source, accepts and recalls it, excludes it from one request, reopens the inspector, sends without the excluded bytes, forgets it, and restarts the host and Store. The final test observes exact preview IDs through bounded observation of unchanged server responses. Foreground and extraction runtimes are deliberately scripted. The result is not live-model usefulness or installed native-client proof.

[PR #516][pr516] repairs request exclusions lost on inspector reopen. [PR #522][pr522] disables conflict-edit controls in read-only reviews. Draft [PR #538][pr538] bridges retained, handled FILE_RANGE evidence that actually entered the settled runtime from an opted-in conversation. It retains exact bytes, range, revision, and current physical grant/owner custody, without an arbitrary file scan or reread. Extraction still produces proposals for review.

The FILE bridge passed tests on its earlier integrated prerequisite cut. Its clean local regression/typecheck processes could not start after the environment outage, and the reconstructed remote tree is explicitly NOT_RUN. It remains draft. Three production blob identities were independently checked, but no complete clean local-to-remote tree match is claimed.

### M06: evidence rejection improved; execution integration remains incomplete

The focused fixes address missing required checks, execution failures overridden by passing siblings, durable repair decisions, unresolved-effect overflow, unsupported screenshot claims, foreign-owner evidence, arbitrary source-root authority, stale read projections, and exact detail visibility. [Service][service], the [read model][read-model], and [SourceWorkbench][workbench] must apply consistent authority, owner, freshness, and live-effect rules.

Historical observations remain visible. Evidence from a different durable thread/project/workspace/account owner cannot certify the current owner. A historical run ID or epoch alone does not invalidate evidence for the same durable owner. [PR #534][pr534] repairs completion and panel consumers; [PR #536][pr536] repairs the Workbench's authority, current-effect, and asynchronous-read boundaries.

The [details UI][panel] exposes argument-preserving JSON, exact cwd and digest identities, timestamps, exit code, bounded detail, and browser expected/observed/viewport fields. Narrow layouts preserve keyboard access and the composer. Artifact references remain inert references, without an invented viewer, arbitrary path reader, or rerun control. See [PR #533][pr533].

There are still no production callers composing `registerRecipe`, `runRecipe`, `runBrowserChecklist`, `admitQaSpawn`, or `BoundedRepairLoop`. The production M07 path records advisory evidence, which cannot certify executed verification. Declaration, completion, and read projections do not supply the missing runner. These are implementation gaps, not consequences of default-off flags alone. See the [runner][runner], [browser interface][browser], [agent-work composition][agent-work], and detailed matrix.

## Corrections to earlier completion claims

Historical receipts remain intact. Their claims require the following narrower interpretation.

| Earlier evidence | Supported interpretation |
| --- | --- |
| [M06-verification.json][historical-m06] describes execution-profile contracts as proven on the approved base and relates the remaining dependency to M03's credential-lease gate. | Reused schemas, policy decisions, and contract tests exist. A production approved backend, selection/profile registry, and compatible launch handles are not established. Missing native build tooling or credentials is not the only gap. |
| [M09-verification.json][historical-m09] treats M06 build/QA as present on the accepted base. | Accepted code is not host composition. Its own hook-injected role-proof boundary remains relevant: Service supplies neither QA proofs nor handlers, so the role is unavailable. |
| `ProjectVerificationService` comments describe composition from an M03 approved backend. | The comment describes an intended integration. No such production composition was found. |
| `BrowserDriver` defines required origin enforcement and the historical M06 receipt describes browser policy. | Injected fixture drivers exercise the interface; they do not prove real fresh-profile isolation, popup/subresource policy, transfers, cancellation, or artifact custody. |
| UI/browser receipts show verification surfaces. | They establish the renderer and harness behavior stated in each receipt. They do not establish generated-project execution, an installed constrained backend, live repair, or screenshot custody. |

The earlier local M06 review note was not published and is not cited as repository evidence. Later source-authority, owner, details, and Workbench repairs have distinct published PRs and source identities. Required screenshot evidence now fails closed when host custody is unavailable, [PR #531][pr531]. A safe blocked result is not proof that the missing custody pipeline is implemented.

## Verification result and its limit

The exact tested tree recorded **4,522 total, 4,185 passed, 275 failed, and 62 skipped**. Every failing test case also failed on unchanged baseline `567498568611bc33379b31a0630dfaf3691b339f`: 251 in the initial comparison and the remaining 24 in a six-file run with 59 passed and 24 failed. Matching failing test identities does not by itself establish an identical root cause for all 251 initial matches. The suite remains failed.

Build, typecheck, UI architecture lint, native worker/checkpoint targets, browser runs, and later owner, Workbench, and digest checks have separate scope entries in the ledger. Counts overlap and are not additive. No final combined run occurred after all changes. Raw local logs and screenshots remain in the unavailable review workspace; this report does not invent downloadable receipts or recreate missing artifacts.

## Conditions still required for release signoff

Release signoff requires the matrix's production gaps to be completed, then tested through their actual paths. M04 needs the remaining request composition and semantic compaction work, with live paired quality and complete auxiliary-cost evidence. M05 needs the exact FILE bridge head validated, fully enabled installed recall/exclude/send and extraction, repeated-task correctness/usefulness against notes-only behavior, and required installed deletion/native evidence. M06 needs authenticated recipe approval/admission, an approved installed execution backend, managed server/browser lifecycle, real browser policy and artifact custody, QA role composition, and bounded repair orchestration.

Platform-specific native tests, live provider runs, and installed acceptance flows retain explicit NOT_RUN or blocked statuses until executed on the relevant source and platform. Default-off activation is a rollout choice; it neither proves nor excuses missing required code. Optional precompute, external recall, and vector experiments may remain disabled. Baseline failures, skipped platform gates, CI failures/pending checks, and the missing combined run remain visible. **No full release signoff is granted.**
